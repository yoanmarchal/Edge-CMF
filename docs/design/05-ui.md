# 05 — Architecture UI (admin)

Audit de l'existant et architecture cible pour `apps/admin`. Le front public
(`apps/frontend`) est traité en fin de document, en second temps.

---

## 1. État des lieux

### Inventaire

| Couche | Fichiers | Volume |
|---|---|---|
| Pages Astro (garde + montage) | 17 `.astro` sous `pages/` | ~12 lignes chacune |
| Proxys JSON | 7 fichiers sous `pages/api/` | logique de validation + RPC |
| Îlots Preact | 16 `.tsx` sous `islands/` | 1 500 lignes |
| Primitives UI | `islands/lib/ui.tsx` | 9 composants, 155 lignes |
| Client HTTP | `islands/lib/adminApi.ts` | 43 lignes |
| Feuille de style | `styles/admin.css` | 781 lignes, un seul fichier |

### Ce qui tient et doit être conservé

Le socle est sain — la refonte proposée s'appuie dessus, elle ne le remplace pas.

- **La séparation page / îlot / proxy** est respectée partout, sans exception.
  La règle « aucun SSR de données dans l'admin » (CLAUDE.md §8) n'est violée
  nulle part.
- **`requireApiSession()`** est le point d'entrée unique des 7 proxys, avec ses
  trois niveaux (`session`, `writeOnly`, `adminOnly`). Bonne abstraction.
- **`proxyResponse()`** documente et résout un vrai piège (realm workerd).
- **`ui.tsx`** a la bonne intention (source unique des éléments récurrents) et
  le bon commentaire d'en-tête. Le problème n'est pas ce qu'il contient, c'est
  ce qu'il ne contient pas encore.
- **Le CSS est natif et moderne** (`@layer`, nesting, `color-mix`,
  `@starting-style`, View Transitions cross-document) sans une ligne de
  dépendance. Les commentaires expliquent les pièges non évidents
  (piste de grille bornée sur `.media-card`, nom de transition distinct pour
  le login). C'est du travail à ne pas jeter.
- **Icônes SSR dans `AdminShell`** : zéro JS pour la navigation.

## 2. Incohérences et dette

Classées par impact sur l'évolutivité. Les références sont vérifiées dans le code.

### 2.1 Le typage s'arrête à la frontière `/api/*` — critique

`CLAUDE.md` §4 impose le RPC typé de bout en bout. C'est vrai jusqu'au proxy,
et faux au-delà : les îlots parlent à `/api/*` en chaînes de caractères, et
`adminApi.get<T>()` demande au développeur d'annoncer lui-même le `T` attendu.

Conséquence directe : **les mêmes formes de données sont redéclarées à la main
dans chaque îlot**.

| Type | Redéclaré dans |
|---|---|
| `TypeDetail` / `TypeDetailData` | `ContentForm.tsx`, `TypeDetail.tsx` (deux noms, une seule forme) |
| `Term` + `Vocabulary` | `ContentForm.tsx`, `Taxonomy.tsx` |
| `TypeRow` | `ContentList.tsx`, `TypesList.tsx` (champs différents !) |
| `NodeRow` / `NodeDetail` | `ContentList.tsx`, `ContentForm.tsx` |
| `UserRow` | `Users.tsx` |

Ajouter un champ à un nœud ne provoque aucune erreur de compilation dans l'UI.
Le `npm run typecheck` passe sur du code qui ment. C'est le point le plus grave
pour l'évolutivité : la règle « zéro `any` » est respectée à la lettre mais
contournée dans l'esprit, par des interfaces locales non vérifiées.

### 2.2 Deux conventions de mutation coexistent

- **Tunnel `_action`** : `nodes`, `types`, `taxonomy`, `users` font tout en
  `POST` avec un discriminant dans le corps (`create`, `update`, `delete`,
  `create-type`, `delete-field`, `set-role`, `delete-vocab`, `delete-term`…).
- **REST réel** : `media` et `settings` utilisent `PUT`, `DELETE`, `?key=`.

Chaque proxy en `_action` est une chaîne de `if (action === …)` qui se termine
par `return Response.json({ success: false, error: 'action inconnue' })`, avec
la gestion d'erreur recopiée à l'identique 4 à 6 fois par fichier
(`pages/api/types.ts` en compte 6, `pages/api/nodes.ts` 5). Ajouter une entité
= copier ce squelette une fois de plus.

### 2.3 Le boilerplate de chargement est recopié 10 fois

Le motif exact, dans `ContentList`, `TypesList`, `Taxonomy`, `Users`,
`MediaLibrary`, `MediaDetail`, `TypeDetail`, `Dashboard`, `Appearance`,
`MediaPicker` :

```tsx
const [data, setData] = useState<T | null>(null);
const [error, setError] = useState<string | null>(null);
const reload = () => { adminApi.get<…>(…).then(r => setData(r.data)).catch((e: Error) => setError(e.message)); };
useEffect(reload, []);
…
{data === null ? <Loading /> : …}
```

Un nouvel écran coûte aujourd'hui ~40 lignes de cérémonie avant la première
ligne utile. Les cinq formulaires de création (`TypeCreateForm`,
`VocabCreateForm`, `TermCreateForm`, `UserCreateForm`, et le bloc « ajouter un
champ » de `TypeDetail`) sont, eux, structurellement identiques à la virgule
près : `useState` par champ, `saving`, `error`, `submit`, redirection.

### 2.4 Le retour de succès est mort

`ContentForm` redirige vers `/content?ok=1` (2 occurrences) — **rien ne lit
jamais `ok`**. `Notice kind="ok"` existe dans `ui.tsx` et n'est utilisé nulle
part. Après création d'un contenu, d'un type, d'un vocabulaire, d'un terme ou
d'un utilisateur, l'écran de destination ne dit rien : la seule confirmation
est que la ligne est apparue dans le tableau.

Symétriquement, **les redirections de droits ne s'affichent pas** : 11 pages
redirigent vers `/?error=droits`, mais `pages/index.astro` ne rend le paramètre
`error` que dans la branche « session nulle » (le formulaire de login). Un
`editor` qui tente d'ouvrir `/types` atterrit sur le tableau de bord sans le
moindre message. Le mécanisme existe, il est branché à vide.

### 2.5 Les mutations sortent du modèle de navigation

8 `window.location.href = …` dans les îlots. Chacun est un rechargement dur qui
court-circuite les View Transitions soigneusement configurées dans `admin.css`
(lignes 592-683). L'admin a une couche d'animation dont la moitié des parcours
ne bénéficie jamais.

### 2.6 Clés de liste manquantes — bug réel

Seuls `FieldInput`, `MediaLibrary` et `MediaPicker` passent `key`. Les
`.map()` de `ContentList` (lignes du tableau), `TypesList`, `Users`,
`Taxonomy` (termes), `ContentForm` (cases à cocher de taxonomie) et surtout
**`ParagraphsEditor`** en sont dépourvus.

Sur `ParagraphsEditor` c'est un bug observable : retirer le paragraphe *n*
laisse Preact réutiliser le DOM et l'état des champs du paragraphe *n+1*.
L'utilisateur voit les valeurs de l'ancien bloc dans le nouveau.

### 2.7 Confirmations destructives incohérentes

Six `confirm()` natifs bloquants — et une répartition arbitraire :

| Action | Confirmation |
|---|---|
| Supprimer un contenu, un type, un utilisateur, un vocabulaire, un média | oui |
| **Supprimer un terme de taxonomie** | non |
| **Supprimer un champ d'un type** (destructif : perte de données) | non |
| Retirer un paragraphe | non |

`MediaPicker` prouve pourtant que le `<dialog>` natif est déjà maîtrisé dans le
projet, animation comprise.

### 2.8 Le titre de page vit à trois endroits

`AdminShell title=` (balise `<title>`), le `<h1>` — tantôt dans la page Astro
(`pages/index.astro`), tantôt dans l'îlot (`ContentList`, `Taxonomy`, `Users`,
`MediaLibrary`, `TypesList`, `Appearance`, `TypeDetail`, tous les formulaires)
— et parfois une troisième fois dans une constante `COPY`
(`TypesList.tsx`, `TypeCreateForm.tsx`).

Quand le `<h1>` est dans l'îlot `client:only`, **la page est entièrement vide
tant que le JS n'a pas booté** : pas de titre, pas de fil d'Ariane, rien. Le
shell SSR (sidebar, topbar) ne sert à rien tant que le contenu principal reste
blanc. C'est gratuit à corriger et très visible.

### 2.9 Les routes sont des littéraux dispersés

`nav[]` dans `AdminShell` est le seul registre, et il ne couvre que les 8
entrées de premier niveau. Les URLs de détail et de retour sont écrites à la
main partout : `/content/edit/${id}`, `/types/${id}`, `/taxonomy/${v.id}/new`,
`copy.backTo`, `/content?ok=1`… Renommer une section demande un `grep` et un
peu de foi. Aucun fil d'Ariane, seulement des `BackLink` ad hoc dont le libellé
est réinventé à chaque écran (« Retour à la liste », « Retour à la taxonomie »,
« Retour à la bibliothèque », « Types de paragraphes »).

### 2.10 Le tableau est copié-collé cinq fois

`ContentList`, `TypesList`, `Taxonomy`, `Users`, `TypeDetail` construisent
chacun leur `<table><thead>…`. Les états vides divergent : « Aucun contenu. »,
« Aucun média. », « Aucun champ pour le moment. » (celui-ci en `.muted`), et
**rien du tout** pour les utilisateurs et la taxonomie — un tableau à en-têtes
seuls, sans explication.

### 2.11 CSS : un fichier, pas d'échelle

781 lignes, ~90 sélecteurs préfixés `.admin-main …`. Aucune frontière de
composant : les styles de la modale média, des cartes de thème, des champs de
formulaire et du tableau se suivent dans le même bloc.

> **Correction (phase 6).** Cet audit affirmait initialement que le préfixe
> `.admin-main` faisait doublon avec la portée `@layer admin`. C'est faux :
> il délimite la zone de contenu face au chrome (sidebar, topbar). Le retirer
> ferait hériter au bouton de déconnexion de la topbar le style des boutons
> d'action. C'est une frontière fonctionnelle, il est conservé.

Surtout, **il n'y a de tokens que pour les couleurs**. Les espacements sont
écrits en dur : on relève `0.25 / 0.35 / 0.4 / 0.5 / 0.55 / 0.6 / 0.75 / 1 /
1.5 / 2 rem` sans règle, et des tailles de police en `0.75em / 0.85em / 0.9em /
1.1rem`. Deux boutons voisins n'ont pas le même `gap` selon l'endroit où ils
ont été écrits.

### 2.12 N+1 et statistiques fausses

- `ContentForm.loadParagraphTypes()` : une requête pour la liste, **puis une
  requête séquentielle par type de paragraphe**, à chaque ouverture du
  formulaire de contenu. 10 bundles = 11 allers-retours avant affichage.
- `Dashboard` compte en chargeant les listes complètes et en lisant `.length`,
  alors que `pages/api/nodes.ts` force `limit: '100'`. **Au-delà de 100
  contenus, le tableau de bord affiche 100.**

### 2.13 Accessibilité

- `FieldInput` branche multiple : le libellé est un `<span>`, les `id`
  (`field_x_0`, `field_x_1`) sont générés mais **jamais reliés** par un
  `<label for>`. Les champs à cardinalité multiple n'ont pas de nom accessible.
- `Notice` n'a pas d'`aria-live` : une erreur apparue après une action n'est
  pas annoncée.
- Aucune gestion du focus après mutation ou fermeture de modale.
- Pas de lien d'évitement vers le contenu principal.

## 3. Architecture cible

Cinq briques. Chacune supprime une catégorie entière de duplication, et aucune
ne remet en cause le pattern page / îlot / proxy.

### 3.1 Contrat d'API typé : `islands/lib/contract.ts`

Une seule déclaration par ressource, **dérivée des lignes Drizzle du
content-worker** — donc jamais réécrite à la main :

```ts
import type { ContentNode, ContentTypeRow } from '@edge-cmf/content-worker';

/** Vue JSON d'une ligne : les Date deviennent des chaînes ISO. */
type Serialized<T> = { [K in keyof T]: T[K] extends Date ? string : T[K] };

export type ContentTypeSummary = Serialized<ContentTypeRow>;
export type AdminNode = Omit<Serialized<ContentNode>, 'fieldsJson'> & { … };

// Le client est typé par ressource, plus par chaîne d'URL.
export const api = {
  types: { list, listWithFields, detail, create, remove, … },
  nodes: { list, detail, create, update, remove },
  …
};
```

Deux points qui font la différence avec une redéclaration en Zod côté
`shared-types` :

- **La dérivation depuis Drizzle est vérifiable.** Renommer une colonne fait
  échouer `tsc` dans l'admin, pas seulement dans le worker (vérifié en
  renommant `contentTypes.label` : `TypesList.tsx` casse immédiatement).
- **`Serialized<T>` corrige un piège réel** : `createdAt` est un `Date` dans le
  worker et une chaîne ISO après sérialisation JSON. Sans la transformation,
  le type mentait sur ce que reçoit vraiment l'îlot.

Les imports du worker sont `import type` : entièrement effacés, rien du code
back n'atteint le bundle client (règle §4 de `CLAUDE.md`). `adminApi` reste en
dessous comme simple transport.

### 3.2 Proxys déclaratifs : `lib/handler.ts`

Un helper qui absorbe la garde, la validation Zod, le relais RPC et le format
d'erreur `{ success, error }` :

```ts
export const POST = mutations({ auth: 'write' }, {
  create: { schema: insertNodeSchema, run: (c, data) => c.api.nodes.$post({ json: data }) },
  update: { schema: updateNodeSchema, run: (c, data) => … },
  delete: { schema: idSchema,         run: (c, { id }) => … },
});
```

Le tunnel `_action` reste — c'est un choix acceptable et cohérent avec
l'existant — mais il devient **déclaratif et typé** au lieu d'être une cascade
de `if`. Les proxys `media` et `settings` gardent leur forme REST, désormais
l'exception documentée plutôt qu'une divergence subie.

### 3.3 Hooks de données : `islands/lib/useResource.ts`

```ts
const { data, error, loading, reload } = useResource(() => api.nodes.list());
const { submit, saving, error } = useMutation(api.nodes.create, { redirect: routes.content.list, flash: 'Contenu créé' });
```

`useMutation` centralise : état `saving`, capture d'erreur, message de succès
et navigation. C'est le point unique où l'on remplacera plus tard
`window.location.href` par une navigation douce compatible View Transitions.

### 3.4 Primitives d'écran : `islands/lib/ui.tsx` étendu + `components/PageHeader.astro`

À ajouter (chacune supprime une duplication identifiée ci-dessus) :

| Primitive | Remplace | Où |
|---|---|---|
| `PageHeader` (**Astro, SSR**) | `<h1>` dans les îlots, § 2.8 | page |
| `Breadcrumb` (Astro, dérivé de `routes`) | `BackLink` ad hoc, § 2.9 | page |
| `<AsyncView>` | le ternaire `null ? <Loading/>` ×10, § 2.3 | îlot |
| `<DataTable columns rows>` | 5 tableaux copiés, § 2.10 | îlot |
| `<EmptyState>` | 4 formulations divergentes, § 2.10 | îlot |
| `<FormScreen>` | 5 formulaires de création jumeaux, § 2.3 | îlot |
| `useConfirm()` (`<dialog>`) | 6 `confirm()` natifs, § 2.7 | îlot |
| `<Flash>` + `aria-live` | `?ok=1` mort, `?error=droits` invisible, § 2.4 | shell |

**Le déplacement du `<h1>` dans la page Astro est la seule modification qui se
voit à l'œil nu** : le titre et le fil d'Ariane s'affichent immédiatement en
SSR, l'îlot ne prend en charge que la zone de données.

### 3.5 Registre de routes : `lib/routes.ts`

```ts
export const routes = {
  content: { list: '/content', new: (type: string) => `/content/new?type=${type}`, edit: (id: string) => `/content/edit/${id}` },
  types:   { list: '/types', detail: (id: string) => `/types/${id}`, new: '/types/new' },
  …
} as const;
```

Alimente la nav de `AdminShell`, les fils d'Ariane, les `BackLink` et les
redirections de `useMutation`. Les libellés de retour se déduisent du registre
au lieu d'être réinventés.

### 3.6 CSS : tokens + partiels

```
styles/
  tokens.css      ← couleurs (existant) + échelles --space-1..6, --text-sm..xl, --radius-*
  base.css        ← shell, typographie, éléments de formulaire
  components/     ← table.css, card.css, media.css, dialog.css, field.css
  motion.css      ← view transitions + micro-interactions (extrait tel quel)
  admin.css       ← @import de l'ensemble, ordre des layers
```

Règle unique : plus une seule valeur d'espacement en dur. Le contenu des règles
ne change pas — c'est un découpage, pas une réécriture.

## 4. Plan de refonte

Chaque phase se termine par un `npm run typecheck` vert et est indépendamment
livrable. Aucune ne modifie le comportement fonctionnel, sauf mention.

| # | Phase | Contenu | Visible ? |
|---|---|---|---|
| 1 | **Correctifs** — *fait* | `key` sur toutes les listes (§2.6, bug), confirmations manquantes sur champ/terme (§2.7), `?error=droits` affiché, `?ok=1` lu ou supprimé (§2.4), N+1 des types de paragraphe et compteurs du tableau de bord (§2.12) | oui |
| 2 | **Contrat + hooks** — *fait* | `contract.ts`, `useResource`, `useMutation` ; migration de `Dashboard`, `TypesList`, `Users` en pilotes | non |
| 3 | **Primitives d'écran** — *fait* | en-tête SSR dans `AdminShell`, `AsyncView`, `DataTable`, `EmptyState`, `FormScreen`, `Field` | oui (fin du flash blanc) |
| 4 | **Migration des îlots** — *fait* | passage à la nouvelle base, suppression des interfaces locales dupliquées | non |
| 5 | **Proxys déclaratifs** — *fait* | `lib/handler.ts`, réécriture des 7 fichiers `pages/api/` | oui (messages d'erreur) |
| 6 | **CSS** — *fait* | tokens d'espacement/typo/rayons, éclatement en partiels | quasi iso-rendu (voir écarts) |
| 7 | **Routes + a11y** — *fait* | `routes.ts`, `requirePage`, nom accessible des champs multiples, annonces, `scope="col"` | partiellement |
| 8 | **Doc** — *fait* | mise à jour de `.claude/skills/admin-screen/SKILL.md` sur le nouveau pattern | — |

Ordre de valeur décroissante : la phase 1 corrige des bugs réels, les phases
2-4 divisent le coût d'un nouvel écran par trois, les phases 5-7 alignent le
reste.

### Livré en phase 1

- `GET /api/stats` (content-worker) — compteurs en SQL, plus de plafond à 100.
- `GET /api/types?expand=fields` — la palette de paragraphes passe de 1 + N
  requêtes à une seule.
- `src/lib/flash.ts` + `src/components/Flash.astro`, monté dans `AdminShell` :
  tout écran atteint par `?ok=` / `?error=` affiche son message **en SSR**.
  Les codes sont traduits par une table ; la query string n'est jamais rendue
  telle quelle.
- Identité stable des paragraphes (`ParagraphEntry.uid`, `toEntries`/`toValues`)
  et `key` sur toutes les listes.
- Confirmation avant suppression d'un terme et d'un champ. Le retrait d'un
  paragraphe reste sans confirmation : il n'est persisté qu'à l'enregistrement
  du formulaire.

### Livré en phase 2

- `islands/lib/contract.ts` — formes de données dérivées des lignes Drizzle
  (`Serialized<T>`) et un appel nommé par endpoint, lectures et mutations
  comprises. Plus aucune URL `/api/…` écrite dans un îlot migré.
- `apps/content-worker` ré-exporte ses types de lignes (`export type { … }
  from './schema'`), en types uniquement.
- `islands/lib/hooks.ts` — `useResource` (avec garde contre les réponses
  obsolètes, et conservation des données affichées si un RECHARGEMENT échoue)
  et `useMutation` (confirmation, `busy`, capture d'erreur, redirection avec
  code flash).
- Pilotes migrés : `Dashboard` (62 → 46 lignes), `TypesList`, `Users`. Les
  interfaces locales `Stats`, `TypeRow`, `UserRow` ont disparu, et les deux
  listes ont enfin un état vide.

### Livré en phase 3

**En-tête d'écran en SSR.** `AdminShell` prend désormais `title`, `chip`,
`description` et `breadcrumb`, et rend lui-même le `<title>`, le `<h1>`, la
description et le fil d'Ariane. Conséquences :

- le titre est déclaré **une seule fois** par page (le suffixe
  « — CMF Edge Admin » n'est plus recopié 17 fois) ;
- plus aucun `<h1>` dans un îlot : la page n'est plus blanche jusqu'au
  démarrage du JS ;
- les `BackLink` aux libellés réinventés sont remplacés par un fil d'Ariane
  uniforme ;
- ajout d'un lien d'évitement (`.skip-link`) vers le contenu principal.

Une exception assumée : `/types/[id]` garde son lien retour côté îlot, parce
que la section parente (`/types` ou `/paragraphs`) dépend du `kind` du bundle,
inconnu du serveur — l'admin n'a pas le droit de faire du SSR de données.
Autre compromis : sur les écrans de détail, le `<h1>` porte ce que le serveur
sait (« Éditer un contenu », le nom machine du type, « Média ») et le nom de
l'entité s'affiche juste en dessous une fois chargé.

**Primitives** dans `islands/lib/ui.tsx` :

| Primitive | Ce qu'elle remplace |
|---|---|
| `AsyncView` | le ternaire chargement/erreur/vide, recopié dans 10 îlots |
| `DataTable` | 5 tableaux copiés-collés ; `rowKey` est **obligatoire**, la clé ne peut plus être oubliée |
| `EmptyState` | 4 formulations divergentes et 2 absences |
| `FormScreen` + `Field` | 5 formulaires de création jumeaux |

**Îlots migrés** : `ContentList`, `TypesList`, `Taxonomy`, `Users`,
`TypeCreateForm`, `VocabCreateForm`, `TermCreateForm`, `UserCreateForm`.

`useConfirm` a volontairement été écarté : `confirm()` n'est pas cassé, et il
n'est plus appelé que depuis `useMutation({ confirm })`. Le remplacer par un
`<dialog>` est désormais une modification d'un seul fichier — ce qui était le
véritable objectif.

### Livré en phase 4

Tous les îlots restants sont migrés : `Appearance`, `MediaLibrary`,
`MediaPicker`, `MediaDetail`, `TypeDetail`, `ContentForm`. `FieldInput` et
`ParagraphsEditor` ne chargent aucune donnée — ils restent des composants de
présentation pilotés par leur parent, et n'avaient rien à migrer.

Deux invariants sont désormais vérifiables par `grep`, et vrais :

- **aucun îlot n'importe `adminApi`** — tout passe par `contract.ts` ;
- **aucune URL `/api/…` n'est écrite hors de `contract.ts` et `media.ts`**.

Les seules `interface` restant dans les îlots sont des `Props` de composant,
le modèle d'édition local des paragraphes, et le `FormData` de `ContentForm`
(une composition de types du contrat, pas une redéclaration).

Nouveautés de cette phase :

- `useCursorList` — pagination par curseur avec accumulation des pages, numéro
  de génération pour invalider les réponses d'un cycle abandonné, et
  `auto: false` pour différer le premier chargement. `MediaPicker` en profite :
  il n'interroge plus R2 tant que sa modale n'a pas été ouverte, alors qu'un
  formulaire peut porter plusieurs champs média.
- `islands/lib/media.ts` — `humanSize`, `isImagePath`, `publicMediaUrl` et
  `mediaFileUrl` (URL d'aperçu versionnée), qui étaient recopiés dans les trois
  écrans médias.
- `MediaDetail` et `TypeDetail` ne gèrent plus leur propre `saving`/`error` :
  la suppression d'un média redirige avec un message flash au lieu d'un
  `window.location.href` nu.

### Bilan chiffré

| Écran | Avant | Après |
|---|---|---|
| `TypesList` | 100 | 52 |
| `Users` | 98 | 73 |
| `ContentList` | 112 | 77 |
| `Taxonomy` | 118 | 88 |
| `MediaDetail` | 179 | 150 |
| `ContentForm` | 236 | 212 |

Les îlots ont fondu de ~25 % en moyenne **tout en gagnant** des états vides,
des confirmations, des boutons désactivés pendant l'écriture et des messages
de succès. Le volume déplacé vit dans `contract.ts` (239 lignes) et
`hooks.ts` (228 lignes) — cette fois écrit une seule fois.

### Livré en phase 5

`src/lib/handler.ts` fournit trois briques : `read(level, handler)`,
`mutations(level, actions)` et `mutation(schema, run)`. Une action se déclare
en trois lignes :

```ts
export const POST = mutations('admin', {
  'create-type': mutation(insertContentTypeSchema, (input) =>
    contentClient().api.types.$post({ json: input })),
  'delete-type': mutation(z.object({ id: machineNameSchema }), ({ id }) =>
    contentClient().api.types[':id'].$delete({ param: { id } })),
});
```

Les 7 proxys passent de **329 à 196 lignes** (−40 %), sans cascade de `if`.

**Changement de comportement volontaire — le seul de cette phase.** Les

## 6. Le composant `Button`

Ajouté après coup, sur constat visuel : « d'un côté des badges, ailleurs des
boutons, rien n'est unifié ».

### Pourquoi c'était incohérent

Le diagnostic n'était pas « il manque un composant » — il y en avait cinq
(`ActionButton`, `ActionLink`, `SubmitButton`, `RemoveButton`,
`LoadMoreButton`). Deux défauts de conception plus profonds :

1. **`badge` était une APPARENCE passée en booléen.** `<ActionButton badge>`
   voulait dire « dessine-le en pilule », pas « cette action est secondaire ».
   L'appelant décidait du rendu, donc chaque écran décidait différemment : la
   suppression d'un média était une pilule, celle d'un contenu un pavé rouge
   plein, celle d'un terme une icône seule. Trois apparences pour un même
   geste.
2. **`ActionLink` ne pouvait PAS être primaire.** Les liens étaient toujours
   des pilules, les boutons toujours pleins : l'apparence dépendait de la
   balise HTML. « Nouveau type de contenu » (un lien) et « Enregistrer » (un
   bouton) sont pourtant deux actions principales.

Et surtout : **la pilule `.badge` servait à la fois d'étiquette informative**
(« multiple », « Paragraphe », « Fichier ») **et de bouton**. La même
apparence pour « voici une information » et « cliquez ici ».

### Ce qui remplace

Un seul composant, deux axes d'**intention** (pas d'apparence) :

| Prop | Valeurs | Sens |
|---|---|---|
| `variant` | `primary` \| `secondary` | importance — une seule primaire par zone |
| `tone` | `neutral` \| `danger` | sémantique — destructif ou non |
| `size` | `md` \| `sm` | densité (`sm` = ligne de tableau) |
| `iconOnly` | booléen | libellé en `title` + `aria-label` |

`Button` rend un `<a>` si `href` est fourni, un `<button>` sinon — **avec
exactement la même apparence**. C'est le cœur du correctif.

Le type impose le nom accessible : `iconOnly: true` exige `icon` et des
`children` de type `string`. Il est impossible de produire un bouton icône
anonyme.

`RemoveButton` et `LoadMoreButton` restent, comme **préréglages** construits
sur `Button` — pas comme variantes concurrentes.

### Conventions appliquées

- Action de création d'un écran de liste, soumission de formulaire, activation
  d'un thème → `primary`.
- Tout le reste → `secondary` (c'est le défaut : un bouton écrit sans variante
  reste discret plutôt que d'aspirer le regard).
- Suppression d'entité → `secondary` + `tone="danger"` : contour rouge, pas un
  pavé plein. Une suppression doit être identifiable sans crier plus fort que
  l'action principale.
- Suppression en ligne de tableau → `RemoveButton` partout. `ContentList` et
  `Users` affichaient un bouton « Supprimer » pleine taille par ligne ; les
  trois autres tableaux utilisaient déjà l'icône seule. Alignement sur la
  forme la plus légère — facile à inverser si le libellé manque.

`.badge` est désormais réservé aux **étiquettes**, jamais cliquable. Le bouton
de déconnexion de la topbar et celui de connexion utilisent le même composant,
rendus en SSR sans hydratation.

**Régression évitée de justesse** : en retirant `.admin-main button
{ background: accent }`, le bouton « Se connecter » — resté un `<button>` nu —
aurait perdu son style. Il est passé en `Button` lui aussi. Il n'y a plus
qu'un seul `<button>` écrit à la main dans l'admin (la tuile de sélection de
média, qui n'est pas un bouton d'action mais une vignette cliquable).

## 5. Front public — pour mémoire

Traité dans un second temps, mais relevé pendant l'audit :

- **`[slug].astro` affiche les noms machine des champs** (`<dt>{name}</dt>`)
  au lieu de leur libellé. Le libellé existe dans la définition du type, il
  n'est simplement pas chargé.
- **`node.body` est rendu en texte brut** alors qu'un type de champ `richtext`
  existe dans la Field API.
- **Le rendu des paragraphes est heuristique** : « le premier champ porte le
  contenu, les suivants sont des métadonnées ». C'est explicitement agnostique
  du bundle — donc structurellement inévolutif, puisqu'un nouveau type de
  paragraphe ne peut pas avoir son propre gabarit. La réponse cohérente avec
  l'esprit Drupal du projet est une résolution de composant par bundle
  (`components/paragraphs/<type>.astro`, repli sur le rendu générique actuel).
- **`FieldValue.astro` code `alt=""` en dur** alors que l'admin collecte
  soigneusement le texte alternatif de chaque image : l'accessibilité est
  saisie côté back-office puis jetée au rendu.
- **404 et 500 font 9 lignes** et n'utilisent pas `Base.astro` (ni en-tête, ni
  thème actif).
- `Base.astro` mentionne encore **Cloudflare Pages** dans un commentaire, alors
  que `CLAUDE.md` note que le déploiement se fait sur Workers.
